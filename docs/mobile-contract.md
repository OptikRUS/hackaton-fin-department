# Контракт игрового Android-клиента

Источник истины — LCTApp, включая встроенный родительский режим. Этот документ
описывает совместимость с текущими запросами игры от 2026-09-29. API отдельного
родительского приложения не переопределяет этот контракт.

## Общие поля и повторы

Методы игрового профиля передают строковый `deviceId` в JSON. Общий каталог
родительских материалов идентификатора не требует. `gameRunId` обозначает
прохождение. Регистрация, загрузка мира/аналитики и ACK используют неизменяемый
`Idempotency-Key`; при повторе ключа и тела возвращается прежний результат,
изменённое тело конфликтует. UUID внутри PostgreSQL — деталь хранения, ответы
с `profileId` в журнале подарков возвращают исходный `deviceId`.
Повторная регистрация того же `deviceId` с новым ключом обновляет поля питомца
в профиле, сохраняя игровую историю. Это позволяет Android завершить миграцию
локальной идентичности, даже если сохранённый им питомец отличается от ранней
регистрации на сервере. Повтор старого ключа не откатывает последующее обновление;
старый ключ с другим телом по-прежнему даёт `409 IDEMPOTENCY_CONFLICT`.

## Архив мира

`PUT /v1/profiles/snapshot` принимает два формата:

- Текущий Android отправляет полный архив: `payloadKind` отсутствует,
  `snapshotFormatVersion=5`, внутри `snapshotJson` находится `formatVersion=5`
  с полным `history`. Backend также принимает архивы версий 1…4.
- Дополнительно backend принимает компактный текущий мир:
  `payloadKind="CURRENT_WORLD"`, `snapshotFormatVersion=1`,
  внутри `snapshotJson` находится `worldFormatVersion=1`.

Строка `snapshotJson` хранится и возвращается без пересборки, включая int64,
Unicode и порядок полей. Сервер проверяет форму и метаданные оболочки; клиент
проверяет полный доменный мир и канонический checksum при восстановлении.
Полный Kotlin HistoryCodec на сервер не переносится.

| Поле текущего мира | Назначение |
| --- | --- |
| `runId` | Прохождение, совпадает с внешним `gameRunId` |
| `state` | Актуальные питомец, деньги, вещи, бюджет, сюжет и учебный прогресс |
| `historySequence` | Граница состояния, совпадает с `throughHistorySequence` |
| `generation` | Поколение мира, меняется при восстановлении даже того же run |
| `parentRewards` | Квитанции применённых подарков для защиты от повторного эффекта |
| `predecessors` | Компактные `{runId,generation,historySequence}` прежних прохождений |
| `checksum` | Контрольная сумма по каноническим правилам клиента |

Полный `history` и старые `archivedRuns` в компактном формате не требуются.
`POST /v1/profiles/snapshot/download` возвращает прежнюю строку и
`payloadKind="CURRENT_WORLD"` для текущего мира; для legacy сохраняется прежняя
форма ответа. `expectedServerRevision=null` допустим только для первого upload.
Повторный upload не увеличивает ревизию, новый принятый upload увеличивает её на 1.

При смене run новый мир должен содержать прежний run в `predecessors` и
корректную ожидаемую ревизию. Поколение предыдущего активного run может измениться
после восстановления до офлайн-перезапуска; само это не означает подмену мира.
Полные старые архивы сохраняют свою прежнюю проверку продолжения.

Пример текущего Android: `src/tests/data/android-legacy-snapshot-upload.json`,
скопированный из LCTApp `docs/backend/examples/snapshot-upload.json`.
`android-current-world-upload.json` остаётся примером дополнительного компактного
формата backend.
Примеры `android-register-profile.json` и `android-analytics-upload.json` в той же
папке скопированы из одноимённых wire examples (`register-profile.json`,
`analytics-upload.json`) Android.

## Аналитика отдельно от backup

`POST /v1/profiles/analytics` принимает сведения зарегистрированного устройства
независимо от наличия/свежести backup. Вход в родительский режим после PIN
может отправить аналитику и запросить оценки, не загружая мир.

Версии: `schemaVersion=1`, `projectionVersion=4`, `evaluatorVersion=1`.
`skills` содержит ровно 12 записей FIN-01…FIN-12. Это наблюдения эпизодов,
не итоговые статусы освоения. Сервер продолжает проверять форму, версии,
ссылки на факты, счётчики, неизменность исходных событий и повторы.

Текущий Android не передаёт `historyStartSequence`; backend использует значение 0.
Для компактного мира после restore backend также поддерживает частичный диапазон:
`historyStartSequence` задаёт отсутствующий префикс. Например, `(900,901]`
содержит факты нового действия 901, но не требует переслать первые 900 записей.
Для старого полного диапазона с началом 0 сохраняется допустимость sequence 0.

Ранее принятые факты не удаляются при отсутствии в префиксе. Отсутствие факта
в заново переданном диапазоне или изменение уже известного eventId — конфликт.
Сервер хранит проекции вместе с границами диапазона; одинаковый конец с разным
началом не должен заменять одну проекцию другой. Счётчики нельзя механически
складывать при повторе пакета или использовать для обнуления старых свидетельств.

Ответ повторяет `batchId`, `gameRunId`, точный `acceptedThroughHistorySequence`
и полный набор `acceptedEventIds`. Новый пакет со старшей принятой границей
не откатывается; более старый новый batch получает `409 STALE_ANALYTICS`.
Идентичный уже принятый batch возвращает собственную квитанцию даже после
продвижения границы. Старые idempotency digests сохраняются при добавлении
полей с отсутствующими/нулевыми значениями.

## Оценки навыков

`POST /v1/profiles/skills/query` возвращает готовые оценки с `gameRunId`,
`basedOnHistorySequence`, ровно 12 FIN-кодами, `status` и `policyVersion`.
Backend рассчитывает `MASTERED`, `PRACTICING`, `NO_DATA`, `HAS_PROBLEM` после
каждой новой принятой загрузки по [политике `skills-mvp-v1`](skill-assessment-mvp.md).
Запрос оценок также обрабатывает ранее принятые проекции без новой загрузки.
При отсутствии аналитики и готовой записи сохраняется `409 ASSESSMENT_NOT_READY`;
принятая пустая аналитика даёт все 12 статусов `NO_DATA`.
`GET /api/parents/{petId}` использует `petId=deviceId` и показывает серверные
оценки для run последнего принятого snapshot. Встроенный режим Android продолжает
получать оценки через `skills/query`.

## Родительские материалы

`GET /v1/parent-materials` доступен без регистрации профиля и независимо от
готовности оценки навыков. Ответ содержит `schemaVersion=1`, непустой
`contentVersion`, `publicationStatus` и `skills`.

Текущая публикация: `contentVersion="2026-09-29-v1"`,
`publicationStatus="PUBLISHED"`, `skills` содержит материалы для всех 12 навыков,
HTTP 200. Публикация материалов не меняет статусы освоения навыков.

`PUBLISHED` требует все 12 уникальных FIN-01…FIN-12. Каждая запись содержит
`skillId`, `learningGoal`, `story`, `replaceWithParentStory`, пять непустых
`conversationStarters`, `parentTakeaway`, `researchBasis` и непустой массив
HTTPS-ссылок `researchSources`. Метаданные и тексты не могут быть пустыми.
В каталоге нет `status`, `isMastered` или питомца. `UNPUBLISHED` требует пустого
массива навыков. Отсутствие `publicationStatus` в заполненном исходном каталоге
трактуется как `PUBLISHED`, но в API статус всегда указан явно.

Отсутствующий файл каталога даёт `contentVersion="unpublished"`,
`publicationStatus="UNPUBLISHED"`, `skills=[]`, HTTP 200. Повреждённый
каталог или ошибка его чтения даёт `503` с
`{"detail":"PARENT_MATERIALS_UNAVAILABLE"}`; импорт приложения, `/health`, backup
и аналитика от наличия материалов не зависят. Загрузка происходит при запросе;
исправленный файл доступен без перезапуска приложения.

Отчёт `/api/parents/{petId}` возвращает зарегистрированного питомца и сохранённые
статусы текущего run. До snapshot `balance` и `visualState` равны `null`; до оценки
все навыки имеют `NO_DATA`. Неизвестный `deviceId` возвращает 404.
Каждый из 12 навыков содержит `materialsAvailable=true` и семь полей материалов
в camelCase из того же каталога независимо от статуса освоения. При отсутствии
публикации `materialsAvailable=false`, строковые поля материалов пусты, списки пусты.
Повреждённый каталог возвращает `503` и в этом методе.

## Награды

Выдача `POST /v1/parent-profiles/rewards` и мобильные `rewards/pull`,
`rewards/ack` сохраняют существующий формат. Для награды run должен быть
зарегистрирован принятым snapshot; аналитика сама по себе не выдаёт подарок.
ACK не удаляет подарок из журнала. Новый мир сохраняет клиентские квитанции,
но сервер не меняет баланс snapshot при выдаче: эффект применяет игра.
Применение монет и дубликатов аксессуаров остаётся отдельной клиентской политикой.

### Кепки родительских квестов — 2026-09-29

Согласовано с [контрактом LCTApp](https://github.com/salyamii/lct2026/blob/f9353fb/docs/backend/parent-rewards.md#кепки-из-figma---каталог-клиента-от-2026-09-29).
`POST /v1/parent-profiles/rewards` принимает все шесть стабильных идентификаторов:

| Предмет | `itemId` |
| --- | --- |
| Кепка с гербом Москвы — синяя | `cosmetic-cap-moscow-blue-v1` |
| Кепка с гербом Москвы — изумрудная | `cosmetic-cap-moscow-emerald-v1` |
| Кепка с гербом Москвы — бордовая | `cosmetic-cap-moscow-burgundy-v1` |
| Кепка ЛЦТ 2026 — синяя | `cosmetic-cap-lct2026-blue-v1` |
| Кепка ЛЦТ 2026 — изумрудная | `cosmetic-cap-lct2026-emerald-v1` |
| Кепка ЛЦТ 2026 — бордовая | `cosmetic-cap-lct2026-burgundy-v1` |

Пример тела с заголовком `Idempotency-Key: <stableRewardRequestId>`:

```json
{
  "deviceId": "9f1c2d3e4a5b6078",
  "schemaVersion": 1,
  "gameRunId": "73d831fd-cf83-4a8c-9e99-973fe16fef4e",
  "reward": {"type": "ACCESSORY", "itemId": "cosmetic-cap-lct2026-emerald-v1"}
}
```

Возраст и окрас питомца не меняют `itemId`: соответствующее изображение выбирает
игра. Цены, URL изображения и автоматическое надевание в запрос не входят.
Старая шляпа исследователя остаётся отдельным аксессуаром.

Идентичный повтор с тем же ключом возвращает исходный grant и sequence;
изменение кепки или run при уже использованном ключе даёт
`409 IDEMPOTENCY_CONFLICT`, если запрос прошёл предварительную проверку
текущего зарегистрированного run. Нецелевой run отклоняется раньше с
`409 GAME_RUN_CONFLICT`, незарегистрированный — с `409 GAME_RUN_NOT_REGISTERED`.
Неподдерживаемый аксессуар по-прежнему даёт `422 UNKNOWN_ACCESSORY`.
Выдача требует зарегистрированного snapshot run; новые кепки проходят обычные
pull/ACK и сохраняются в журнале после ACK. Схемы JSON и БД не меняются.

Игровой клиент после выдачи сразу применяет grant к актуальному инвентарю
и отправляет ACK только после локальной транзакции. Уже принадлежащую кепку
клиент не предлагает к начислению; при гонке доставки создаёт `ALREADY_OWNED`
без второго предмета. Backend не выводит актуальное владение из потенциально
устаревшего snapshot и не дедуплицирует разные запросы по `itemId` — повтор
HTTP защищён `Idempotency-Key`, повтор эффекта в игре защищён receipt.
Отдельному родительскому приложению немедленное локальное обновление не требуется.

## Проверки перед публикацией

Использовать отдельную PostgreSQL: pytest применяет миграции и откатывает её
до base после завершения. Проверять текущий клиентский JSON, legacy-повторы,
первую аналитику без snapshot, аналитику впереди backup, частичный диапазон
после restore, смену run и доставку подарка после нового мира. Production-записи
не нужны для этих проверок.
